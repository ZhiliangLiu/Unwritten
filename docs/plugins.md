# Unwritten · 插件

本文说明 Unwritten 的插件是什么：插件和 core 的边界、所有插件协议共同遵守的规则、插件必须履行的义务、仓库里的插件怎样组织，以及怎样新增一个插件或一种插件。具体的协议写在它所属领域的文档里，例如出图服务的协议见[插图与出图服务 §3](./image.md#3-unwritten-图像协议)；具体的插件各有自己的文档，例如 [ComfyUI 插件与 Colab 部署](./comfyui-plugin.md)。

一句话概括：**插件是实现了 Unwritten 协议的独立服务，不是载入 core 的代码；core 只认协议和能力，不认插件。**

## 1. 什么是插件

插件是一个独立运行的网络服务。它实现 Unwritten 定义的某一种协议，core 像调用模型服务一样，凭一个地址和一个 key 调用它。

| 插件的种类 | 协议 | 协议规范 | 一致性测试 | 现有的插件 |
| --- | --- | --- | --- | --- |
| 出图服务 | `unwritten-image/1` | [插图与出图服务 §3](./image.md#3-unwritten-图像协议) | `packages/core/src/image/conformance/` | [ComfyUI 插件](./comfyui-plugin.md) |

**为什么是服务，而不是代码。**

- **安全。** core 持有全部 key 和全部故事数据（[架构总览 §2.1](./architecture.md#21-本机接口的安全)）。载入第三方代码，就等于把这些都交了出去。
- **语言和运行位置不受限。** 插件要包装的东西，往往用别的语言写，或者必须跑在别的机器上。出图引擎是 Python 写的，跑在有 GPU 的机器上。代码插件省不掉这一层进程边界，反而要多维护一套插件 API、版本兼容和 Electron 打包。
- **崩溃隔离。** 插件崩了、卡了，core 和界面照常运行，最多是这项能力暂时不可用。

**插件不是第五个组成部分。** 四个组成部分是 client、core、contracts、desktop（[架构总览 §1](./architecture.md#1-四个组成部分)）。插件和模型服务一样是 core 调用的外部服务，没有插件，应用照样完整可用。

## 2. 边界

| 方向 | 规则 |
| --- | --- |
| core 调用插件 | 只经过协议。core 看到的只是地址、key 和插件报告的能力 |
| 插件调用 core | 不允许。插件不知道 core 的地址，也没有 core 的令牌 |
| 插件访问数据 | 不允许。插件拿不到数据目录、作品库和 `providers.json`，只收到协议请求里的那些内容 |
| client 与插件 | 设置页可查看配置地址。client 只请求 core，由 core 发出插件请求和转交结果 |
| 代码共享 | 没有。插件不导入仓库里的任何 TypeScript 代码，core 也不导入插件的代码；两边只共享协议规范 |

两条由测试守住的规则：

1. **core 的行为只由能力字段决定，从不按插件的实现名分支。** 插件报告的实现名和版本，只用来在设置页显示。
2. **`apps/` 和 `packages/` 的源码里不出现任何插件专属的名字。** 一条测试扫描这两个目录，命中插件目录名或它依赖的部署工具名（例如 `comfy`、`colab`、`tailscale`）就失败。`plugins/` 不在扫描范围内。每新增一个插件，就把它的名字加进这条测试的清单。

## 3. 协议的共同规则

每一种插件协议都遵守本节的规则，各自的规范只写这种协议独有的部分。

### 3.1 地址、版本与传输

- **路径带主版本号。** 所有路径挂在服务地址的 `/v<主版本>` 下，协议名写成 `unwritten-<种类>/<主版本>`，例如 `unwritten-image/1`。
- **同一主版本之内只增不改。** 只能增加可选的字段；调用方忽略不认识的响应字段，插件忽略不认识的请求字段。新增的请求字段必须由一个能力字段开放，core 只在插件声明支持时才发送。要做不兼容的改动，就换一个主版本号，core 可以同时支持新旧两个版本。
- **请求和响应默认是 JSON。** 二进制结果走单独的取数接口，直接返回字节。
- **不返回重定向，也不返回 CORS 头。** 只有 core 调用插件，浏览器不直接访问；core 的外发请求本来也不跟随重定向（[LLM 端点 §3](./llm-endpoints.md#3-key-的来源与保护)）。
- **大块数据内联传送。** 请求里不带任何 URL，插件不替调用方访问外部地址。

### 3.2 鉴权

- **每个请求都带 `Authorization: Bearer <令牌>`，** 包括读取信息的接口。令牌不出现在 URL 里。
- **插件用常量时间比较令牌，** 不匹配就返回 401 `unauthorized`。令牌不足 32 个字符时，插件拒绝启动。
- **令牌由 core 生成。** 设置页生成 32 字节随机数（base64url 编码），只显示这一次供用户复制到插件一侧。保存后按 key 的规则保护（[LLM 端点 §3](./llm-endpoints.md#3-key-的来源与保护)）。

### 3.3 信息接口

每种协议都有 `GET /v<主版本>/info`，至少返回：

```json
{
  "protocol": "unwritten-<种类>/<主版本>",
  "implementation": { "name": "<实现名>", "version": "<插件版本>" },
  "ready": true,
  "notReadyReason": null,
  "capabilities": {}
}
```

- **`ready` 为 false 表示插件在线但暂时不能工作，** 例如正在启动或正在自检。`notReadyReason` 从这种协议规定的原因里取值。core 把「未就绪」和「连不上」区分开，给出不同的提示。
- **`capabilities` 的字段由各协议定义。** core 的一切行为差异都来自这里。

### 3.4 有副作用的请求

- **带幂等键。** 会产生副作用或消耗资源的请求带 `idempotencyKey`：同一个键、同样的请求体，返回同一个结果；同一个键、不同的请求体，返回 409 `idempotency_conflict`。插件至少记住这个键到结果过期为止。网络一抖、core 重发请求，插件不会把同一件事做两遍。
- **耗时的工作走任务。** 提交后立即返回任务 id，再由调用方查询状态和结果，支持取消。任务 id 是不可猜的随机值。这样一次工作的耗时不受任何一段网络连接的超时限制。

### 3.5 错误

- **错误响应的格式统一为** `{ "error": { "code": "...", "message": "..." } }`。
- `code` 从协议规定的清单里取值；`message` 只供排查，core 不显示它，也不当作数据记录。
- 共同的错误码：`unauthorized`（401）、`invalid_request`（400）、`idempotency_conflict`（409）、`busy`（429，带 `Retry-After`）、`not_ready`（503）、`not_found`（404）。各协议可以在此基础上增加自己的错误码。

### 3.6 一致性测试

每种协议都配一组一致性测试，放在 core 里实现这种协议的模块下面，逐条覆盖它的规范和本节的共同规则。

- 默认对着 core 自带的伪服务运行，进入日常测试。
- 设了 `UNWRITTEN_<种类>_CONFORMANCE_URL` 和 `UNWRITTEN_<种类>_CONFORMANCE_TOKEN` 时，对着那个地址运行，用来验收真实的插件。
- **插件能不能接入，只看能不能通过这组测试。** core 不为任何一个插件开例外。

## 4. 插件的义务

除了遵守协议，每个插件还必须做到：

- **最小的对外面。** 对外只暴露协议规定的接口。它包装的引擎（例如 ComfyUI）只监听回环地址，不对外。
- **调用方只能填参数。** 不接受调用方提交的脚本、工作流或任何可执行的内容，所以令牌泄露时，别人也只能使用协议规定的能力。
- **每个输入都有上限：** 长度、数量、字节数、排队数；内联的数据实际解码校验，不信请求里声明的类型。
- **不留下用户内容。** 请求里可能有故事内容，所以插件不把请求和结果写进持久存储，不写进日志，结果过了保留期就丢弃。输出的文件格式能携带元数据时（例如图片），去掉全部元数据。
- **供应链钉死。** 依赖、模型和它包装的引擎都钉到具体版本；从网络下载的文件核对哈希；不在运行时在线安装扩展。
- **自检。** 启动后先用不含用户内容的固定输入把自己跑通一遍，通过后才报告 `ready`。

## 5. core 怎样对待插件

- **插件的返回是信任边界。** core 按协议逐项校验返回的数据，类型、大小、格式不对就拒收，不信插件报告的元信息（[插图与出图服务 §5.3](./image.md#53-校验返回的数据)）。
- **配置和 key 的规则照搬模型服务。** 插件服务和 LLM 端点写在同一个 `providers.json` 里，适用同一套 key 规则：key 不出 core，地址保存后不能改，明文 http 访问非本机地址时警告（[LLM 端点 §3](./llm-endpoints.md#3-key-的来源与保护)）。
- **外发请求只走 `net` 模块。** 不跟随重定向，有时间上限，可以取消（[插图与出图服务 §5.2](./image.md#52-外发请求)）。
- **插件常常不在线。** 插件是可选的增强：连不上时，依赖它的那项能力降级，应用的其他部分照常运行；core 记住最近一次的连接结果，离线时快速失败，不让每个请求都等到超时。
- **只看能力。** 插件报告的实现名和版本只在设置页显示，方便核对插件的版本（§2）。

## 6. 仓库里的插件

```
plugins/
  <插件名>/
    README.md      入口地图：它是什么、实现哪种协议、怎样运行
    ……             插件自己的代码、配置、锁定文件和测试
```

- **一个插件一个目录，** 目录名就是插件名，用 kebab-case。设计细节写在 `docs/` 下这个插件的文档里，README 按[根目录 AGENTS.md §9](../AGENTS.md#9-源码目录的-readme) 只做入口地图。
- **插件有自己的工具链。** 插件可以用另一种语言，依赖和版本锁定在插件目录里，不进 `pnpm-workspace.yaml` 的 catalog。用到的语言和工具写进[技术选型 §3](./tech-stack.md#3-仓库与工具链)。
- **全仓的规矩照样适用：** 不写注释，key 不进仓库，测试和示例里的故事内容一律虚构（[根目录 AGENTS.md §7](../AGENTS.md#7-贯穿性硬纪律)、[§8](../AGENTS.md#8-不写注释)）。
- **CI 对每个插件做两件事：** 跑插件自己的测试；启动插件（对外部引擎用伪实现替代），再对着它运行这种协议的一致性测试（§3.6）。
- **版本。** 插件的版本写在它自己的配置里，并在信息接口的 `implementation.version` 里报告。插件和 core 之间只靠协议的主版本号保持兼容，不要求两边同时发布。

## 7. 新增插件

**新增一个插件**（实现一种已有的协议）：

1. 在 `plugins/` 下建目录，写 README。
2. 在 `docs/` 下写这个插件的设计文档，并加进[文档索引](./architecture.md#文档索引)。
3. 把插件名和它专属的部署工具名，加进 §2 那条扫描源码的测试的清单。
4. 在 CI 里接上它的测试和一致性测试。

core 一行都不用改。

**新增一种插件**（定义一种新协议）：

1. 在所属领域的文档里写协议规范，只写这种协议独有的部分，共同规则引用本文 §3。
2. 定义 `capabilities` 的字段和 `notReadyReason` 的取值，并说明 core 怎样按能力降级。
3. 在 core 里加实现这种协议的模块、伪服务和一致性测试；外发请求经过 `net` 模块。
4. 在 `providers.json` 里加这种服务的配置，在设置页加对应的一节。
5. 更新 §1 的表。

## 8. 不做的事

- **载入 core 的代码插件。** 理由见 §1。
- **插件市场、自动发现和在线安装。** 插件由用户自己部署，再在设置页填地址和令牌。自动发现要扫描网络，在线安装就是在运行时下载代码执行，两者都扩大攻击面。
- **插件反过来调用 core。** core 只监听本机回环地址，令牌只证明「是本次启动打开的页面」（[架构总览 §8](./architecture.md#8-不做的事)）。让外部服务调用 core，需要另一套鉴权。
- **client 直接连插件。** 插件请求和凭据由 core 统一管理。
- **插件访问数据目录。** 插件需要的东西，都由 core 放进协议请求里。

## 9. 验收

| 从什么情况开始 | 操作 | 应当看到的结果 |
| --- | --- | --- |
| 任意一个插件 | 对它运行所实现协议的一致性测试 | 全部通过 |
| 一个不校验令牌、或返回重定向的伪插件 | 运行一致性测试 | 对应的用例失败 |
| 一个插件把 `implementation.name` 换成别的名字，能力不变 | 走一遍用到它的功能 | core 的行为没有任何变化，只有设置页的显示变了 |
| 在 `packages/core` 里写一个插件名的字符串 | 运行测试 | 扫描源码的测试失败 |
| 插件离线 | 使用依赖它的功能，再使用应用的其他功能 | 依赖它的功能很快提示连不上；其他功能照常 |
| 插件已经保存 | 打开设置，再预览一张图，查看 client 的网络面板 | 设置接口返回配置地址。所有请求都发往 core，响应没有已保存的令牌 |
