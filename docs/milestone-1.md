# Unwritten 第一个里程碑：从一句背景到重启续玩

**目标：** 维护者能从空数据目录启动，在设置里接入真实模型，写一句背景，采用 AI 写的开场，连续游玩三个回合。退出并重启 core 后，从正确的决定点接着玩，并在后续剧情里看到先前行动的后果。这条路径同时检验作者能否自行配置模型、低成本做出一部作品，以及玩家是否愿意继续读、继续行动。

交付给维护者在本机试用。用浏览器打开独立运行的 core 所提供的 client。先验证同一部作品能从创作走到续玩，把桌面交付留给后续。[架构总览 §2.2](./architecture.md#22-core-独立运行)

## 作者和玩家能做什么

| 环节 | 可交付的体验 |
| --- | --- |
| 配置模型 | 从作品库打开模型设置，新增一个自定义端点。手填名称、OpenAI 兼容地址、模型 ID 和可选的 API key，可测试连接与工具调用，保存后将该模型用于开场生成和续写。设置页显示当前模型，允许更新模型或凭据，也可以新增端点后切换。 |
| 写背景 | 从作品库新建草稿，只填一段可用于玩家叙事的背景。开始生成前保存这段原文，退出后能找回。 |
| 预览开场 | 一次生成一份预览，包含标题、简介、简短的公开设定、开场正文和推荐行动。作者可以改背景再生成，也可以采用预览并存入作品库。预览生成和保存是两个动作，只有作者保存后才能正式开局。 |
| 连续游玩 | 从作品库打开已采用的开场，此时就可以退出并续玩。每部作品提供一个正式开局，其下只有一条路线。玩家可点选推荐行动，也可自由输入。阅读页按顺序保留开场、实际行动和完整回应，只在最新决定点提供操作。 |
| 离开和回来 | 等待时显示已提交的行动。生成失败后保留该行动和上一个完整决定点，可以重试。重新打开作品时，从 SQLite 读取最新已提交的进度。 |

把故事方案确认和开场采用合在一次预览里，少做一套生成任务和编辑界面。代价是作者调整叙事方向时，需要改背景并重新生成整份预览。完整向导的交互依据见[创作流程 §3–4](./authoring-flow.md#3-确认故事方案再生成开场)和[游玩流程 §1–2](./gameplay-flow.md#1-进入作品找到正确的起点)。

模型设置支持 `openai-completions` 自定义端点，开场生成和续写共用一个默认模型。手填模型 ID 省去目录和发现流程，用户需要事先知道模型 ID。测试连接用一次最小工具调用检查地址、凭据和模型能力。缺少可用配置时，生成入口说明原因并提供设置入口，作品库和已有剧情仍可打开。[LLM 端点 §6–7](./llm-endpoints.md#6-自定义端点)

## 实现顺序与检查点

1. **启动并打开作品库。** 用 pnpm 搭起 client、core 和 contracts。core 从指定数据目录启动，先打开诊断库，再打开并迁移作品库，随后提供构建后的 client，通过 oRPC 契约读取空作品库。用生产构建验证带令牌的入口、回环监听、Host 与 Origin 检查以及内容安全策略。[架构总览 §2.1–3](./architecture.md#21-本机接口的安全) · [技术选型 §3](./tech-stack.md#3-仓库与工具链)
2. **从设置接入模型。** 通过 oRPC 契约读取配置、测试连接、保存端点并设置默认模型。core 校验配置修订、原子写入 `providers.json`，通过 `llm.config_changed` 通知已打开的页面。编辑时留空 key 保留原值，移除 key 使用显式操作，更换地址时新建端点。接口响应只返回 key 状态，日志记录前脱敏。连接测试和实际调用都走 `llm` 模块的重定向检查。配置变更从下一次模型请求生效。[LLM 端点 §2–3](./llm-endpoints.md#2-providersjson) · [LLM 端点 §7](./llm-endpoints.md#7-用途分配) · [LLM 端点 §10](./llm-endpoints.md#10-core-接口)
3. **从草稿得到可玩的开场。** 用默认模型生成预览。预览绑定生成时的草稿修订号，改过背景后须采用基于当前草稿的预览。采用时在一个事务内保存发布版本并更新作品的发布指针。固定开场直接成为根回合，连同首条路线一起保存。[创作工作站 §9](./author-workstation.md#9-生成任务) · [数据模型 §2–3](./data-model.md#2-作品与版本) · [回合循环 §10](./turn-loop.md#10-开场)
4. **提交回合并恢复进度。** 续写读取该开局的发布版本、当前行动和这条路线的祖先回合。模型用字符串参数调用 `propose_turn`，core 校验正文和选项，在同一事务里追加完整回合、推进路线 head、标记请求完成。请求幂等键和预期 head 在 core 生效。单条事件流通知 client 变化，重连后重新查询。core 重启时把未完成的请求标记为中断，重试沿用原请求。[回合循环 §1–3](./turn-loop.md#1-一回合的流程) · [回合循环 §5–8](./turn-loop.md#5-提交一回合propose_turn-与-ask_clarification) · [架构总览 §3](./architecture.md#3-client-与-core-的通信)

交付包含[运行诊断和性能样本](./diagnostics.md)。主路径从首次启动就记录 core 和 client 的读数，能按任务或请求 ID 复查排队、模型首输出、校验、提交和界面呈现。用量和单次模型调用总耗时沿用 `llm_calls`，用调用 ID 串起两处记录。

近期剧情直接用原文维持连贯性。上下文按模型预算从最新的回合向前取，保留发布版本中的硬设定、当前行动和最新回合。必要材料放不下时明确报错，路线仍停在原处。作品正文、玩家输入和模型输出以纯文本呈现。界面沿用文案、token、键盘焦点和状态播报规则。[回合循环 §3](./turn-loop.md#3-上下文哪些直接给哪些让模型查) · [client 编码规范](../apps/client/AGENTS.md)

## 留给后续的能力

| 能力 | 推迟的理由 |
| --- | --- |
| Electron、安装包、自动更新 | 独立运行的 core 和浏览器足以验证创作与游玩，桌面交付有独立的验收目标。 |
| 内置服务商目录、端点预设、模型发现、Anthropic 原生协议和多用途分配 | 手填一个 OpenAI 兼容端点即可完成设置和验证，开场与续写共用默认模型。 |
| 独立的故事方案、创作工作站、试玩、发布后改稿 | 采纳开场前的预览已经提供作者控制点。草稿和发布版本的边界从第一次保存就保留。 |
| 重新开局、手动存档、从存档另开、换一种发展和结局 | 一条持续追加的路线足以验证行动、回应和自动续玩。开局、父回合和路线 head 按既有数据模型保存。 |
| 结构化事实、幕后设定、知情、状态栏、手记、检索和后台摘要 | 公开设定和短历史足以验证近期后果。跨长历史的一致性和防剧透需要单独验收。 |

## 验收

| 从什么情况开始 | 操作 | 应当看到的结果 |
| --- | --- | --- |
| 空数据目录 | 在设置里填入真实端点和模型 ID，测试连接并保存，随后重启 core | 设置页确认工具调用可用。重启后仍显示并使用同一默认模型，读取配置时只显示 key 状态。全程通过界面完成。 |
| 已配置默认模型 | 分别用错误的 key 和返回无效工具调用的伪服务商测试连接。另用无效 JSON 代替临时数据目录里的模型配置，再从设置页尝试保存 | 连接测试分别给出失败原因和处理方式，并保留现有配置。无效配置显示出错位置，设置页拒绝覆盖文件，已有剧情仍可阅读。 |
| 默认模型已通过测试 | 写一句关于雨夜修钟铺的背景，生成预览，改一次背景，再生成并采用开场 | 草稿保留作者原文。旧预览无法发布，新预览有符合背景的完整开场和可执行的推荐行动。作品保存后可从作品库打开，开局显示刚采用的开场。 |
| 开场已保存 | 先点一次推荐行动，再自行输入一项会改变后续场景的行动，例如把备用钥匙交给学徒。完成第三个回合后重启 core，再行动一次，例如请学徒用那把钥匙开门。 | 重启后看到相同的已提交全文、行动原话和最新决定点。新的回应接得上钥匙的去向，并把主角的下一个重要决定留给玩家。 |
| 回合等待提交 | 用伪服务商分别模拟无效输出和中途中断。重启后重试，同时检查重复提交和过期的预期 head。 | 任一失败都保留上一个完整决定点。重试成功只新增一个回合，重复请求返回已有结果，过期请求不会移动路线。 |
| 一部作品已有进度，另有一部作品 | 交替打开两部作品，并检查各自的续写上下文 | 两部作品只看到各自的开场、设定和行动。 |
| 同一临时数据目录完成生成、失败重试和重启 | 查询诊断库中的运行事件与性能样本，并检查数据目录 | 能按请求 ID 区分各次尝试及其结果，用调用 ID 查到对应的 `llm_calls`，重启后仍能读取。运行、调试与性能记录都没有落为日志文件。 |
| 生产构建正在运行 | 检查缺少令牌和来源不符的请求。用键盘走完主路径，并在中文输入法组字时按回车。 | 不合要求的接口请求被拒绝。可见焦点清楚，生成完成和失败可被播报，组字回车不会提交。 |

验收分两部分。用伪服务商和临时数据目录跑浏览器端到端测试，从界面配置模型开始，验证到重启续玩的数据闭环及失败恢复。再用真实模型手动走一遍，判断开场是否值得继续读、自由行动能否被接住、重启后的剧情是否承接先前行动。[技术选型 §8](./tech-stack.md#8-测试) · [可访问性 §11](./a11y.md#11-测试)
