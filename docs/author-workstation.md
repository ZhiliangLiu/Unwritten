# Unwritten · 创作工作站

本文说明创作时 AI 的工作方式：右侧的对话面板、提案卡，以及内容怎样写入草稿。作者看到的流程见[创作流程](./authoring-flow.md)，草稿的存储结构见[数据模型 §2](./data-model.md#2-作品与版本)。

## 1. 定位

**创作向导是主路径，工作站是它旁边的对话面板**，而不是唯一的 AI 入口。原因是创作流程定下的“最短路径”——只写一句背景的作者，不聊天也能一路点完，得到可玩的作品。工作站服务的是另一种需求：“用自然语言告诉 AI 想改什么”。

四条铁律：

1. **AI 只提议，不写入。** 写入草稿只在作者确认提案卡之后发生，执行写入的是普通代码，不经过模型。
2. **卡上逐项列出要改的内容**，例如“修改 5 处设定”这种只给数量的写法不合格。
3. **作者设定优先于 AI 建议。**
4. **幕后设定折叠时，AI 也看不到内容**（§6），所以它不可能在对话里说漏嘴。

## 2. 页面结构

- **主区**是创作向导的各个步骤：背景、方案、开场、试玩、保存。
- **右侧**是工作站面板，可以折叠，也可以拖拽调宽。

切换向导步骤时面板不换，对话原地接着进行。确认提案卡之后，主区自动切到改动所在的步骤，让结果落在作者眼前。

## 3. 对话线程与锚点

**线程。** 一部作品的草稿有一组对话线程，打开时默认接上最近活跃的那一条。“新对话”会开一条新线程，旧线程保留，随时可以切回去。

**锚点**由三部分组成：作者发消息时所在的向导步骤、当时选中的对象（开场里的某一段、某个人物等），以及幕后设定是否已展开。锚点随每条作者消息一起保存，决定这一轮的三件事：

1. 挂载哪些提案工具（§6）；
2. 只读工具的范围：在试玩步骤里，可以多读当前这次试玩；
3. 提案卡的目标。

**目标永远来自锚点，不来自模型。** 提案卡的目标取自**发起提议那一轮**的锚点。作者发完消息就切到别的步骤，卡片稍后才出现，这时按的仍是发起时的目标。作者确认时，按卡上固定的目标执行，切到哪个步骤再确认都不会改错对象。模型自始至终不给出任何 id。

## 4. 两种入口

| 入口 | 例子 | 出卡吗 |
| --- | --- | --- |
| 向导按钮 | 生成故事方案、确认方案并生成开场、再来一批开场候选、采用这个开场、开始试玩、存入作品库 | 不出卡。作者点按钮本身就是授权，参数也全在向导里 |
| 对话里的提议 | “保留这个世界，让两位主角开场就是旧识” | 出卡，等作者确认 |

**向导按钮不经过对话模型。** 所以对话用的模型能力弱，或者干脆没配置，向导照样能走完。按钮的参数都是齐的，作者点下去本身就是授权，再弹一张卡让作者确认一遍是多余的。

## 5. 提案卡

**怎样产生。** 模型在回复中调用提案工具（§6）。提案工具只生成卡片，不写库，参数一律用字符串。

**卡上有什么：**

- 一句话说明意图；
- 目标，取自锚点，例如“人物：沈岚”；
- 逐项改动，每一项给出修改前后的对比；
- 受影响的地方（§7）；
- 缺少的信息，以问题形式列出。选项由 core 从草稿数据中填充，模型只说明要问什么，不负责编选项。

**生命周期：**

- **卡片不阻塞对话。** 作者可以不理它继续聊，也可以点“搁置”。
- **同一线程里出现新卡时，旧的待确认卡失效**，只有最新的一张可以确认。
- **确认在一个事务里完成：**
  1. 登记执行权（`card_claims` 以卡片 id 为主键，重复确认时返回第一次的结果）；
  2. 按动作注册表校验作者的回答；
  3. 执行器写入草稿；
  4. 写一条作者应答消息和一条回执。

  任何一步失败都整体回滚，卡片仍是待确认状态，可以再次确认。
- **确认前再查一次：** 这个动作还存在，目标还在，卡片锚点所在的步骤仍允许这个动作，目标和出卡时相比没有被改过。实体、事实、状态定义、设定小节比较 `rev`；方案、开场这类没有单独修订号的 `meta` 字段，比较卡上记录的修改前内容和当前内容。目标已被删除时如实报错；目标在出卡后被改过时，卡片失效，提示“目标已被修改，请重新提议”，不拿旧的对比结果覆盖作者的新改动。
- **确认按钮灰掉时，必须在卡上写明原因**，指出是哪一项缺了什么。
- **执行后不自动让 AI 回复**，回执已经说明了结果。

**回放历史时保留卡片轮次的真实形状。** 带卡的那一轮要按“文字 + 工具调用 + 工具结果”原样回放给模型，不能压成纯文本。否则模型在历史里只看到“我来出一张卡”这样的话，却看不到真实的调用，就会学着只说不做。如果某一轮回复说了要出卡，却没有调用任何提案工具，就插入一条系统提示，并提供“重试”。

**动作注册表。** 每个动作登记以下内容：

- 参数；
- 在哪些步骤可用；
- 校验规则；
- 执行器；
- 执行后切到哪个步骤。

提案工具的 schema、答案校验、执行和回执都从注册表生成。client 的卡片组件是通用的，只认识问题、选项、前后对比和受影响列表。新增一种能在对话里完成的修改，只需在注册表里加一项。

## 6. 工具

**只读工具**看到的是作者视角下的草稿：

| 工具 | 返回 |
| --- | --- |
| `get_background` | 背景原文 |
| `get_settings` | 某一节补充设定 |
| `get_plan` | 故事方案，每一项带来源 |
| `list_entities` / `get_entity` | 作者设定的人物、地点，含称呼、关系、秘密 |
| `get_opening` | 已采用的开场和候选开场 |
| `get_state_defs` / `get_key_scenes` / `get_ending` | 状态栏定义、关键场面、结束条件 |
| `read_trial_turn` / `search_trial` | 仅在试玩步骤可用：当前这次试玩的路线，叙述者视角 |

**幕后设定折叠时**，秘密只返回无剧透标题（`facts.data.title`），人物的幕后身份也只给标题。作者展开幕后设定后，从下一轮开始才返回全文。所以要修改秘密的提议，只能在作者展开幕后设定之后提出；卡片上会提示“需要先查看幕后设定”。

**提案工具：**

| 工具 | 在哪些步骤可用 | 卡上显示 | 确认后 |
| --- | --- | --- | --- |
| `propose_setting_edit` | 背景、方案 | 这一节修改前后的对比 | 写入 `meta.settings`，修订号加一 |
| `propose_plan_edit` | 方案 | 每一项修改前后的对比，以及来源 | 写入 `meta.plan`，这些项的来源改为 `author_confirmed` |
| `propose_entity` / `propose_entity_edit` | 方案、开场 | 字段表、受影响的开场句子与状态栏目 | 写入实体行，修订号加一 |
| `propose_opening_edit` | 开场 | 修改后开场的完整预览：正文、初始状态、第一组选项 | 作为一个新候选加入，作者在候选里决定是否采用 |
| `propose_from_trial` | 试玩 | 见 §10 | 见 §10 |
| `report_conflict` | 任意步骤 | 两段作者原话并列，以及受影响的体验 | 不写入，由作者就地修改其中一条 |

## 7. 受影响范围与开场核对

创作流程要求：改了会影响开局的设定后，要指出受影响的正文、状态和选项。实现方式是给每个对象记修订号：

- **每个对象都有修订号。** 实体、事实、状态定义各有 `rev` 字段，补充设定的每一节也有自己的修订号。
- **采用开场时，记下它引用的对象和修订号**，包括正文和选项里出现的人物（按称呼匹配）、初始状态涉及的栏目，以及开场所依据的设定小节。
- **被引用对象的修订号一变，开场就标为“待核对”**，并列出受影响的地方：含有该人物称呼的句子、相关的状态栏目、相关的选项。作者写过的文字原样保留，怎么改由作者决定。
- **提案卡上的“受影响的地方”用同一套计算。** 上面这些引用是确定能找出来的部分。模型也可以补充它认为受影响的地方，但 core 只保留确实存在的条目。
- **主角填写项用占位符引用。** 主角的名字等项目留给玩家填写时，作者在开场里通过界面插入占位符（显示为「主角名」这样的标签，存为 `{{protagonist.<项目名>}}`），开局时替换成玩家填写的值（[回合循环 §10](./turn-loop.md#10-开场)）。
- **开场里出现按设置不该固定的名字时，也要标出。** 例如主角姓名留给玩家填写、人物设为每局生成，作者原文的开场却写死了具体名字，就标出这些句子。作者可以换成占位符或通用称呼，或者调整对应的设置。存入作品库前再检查一次，仍有没处理的句子时提示作者。

## 8. 冲突处理

- **AI 的建议和作者设定冲突时，以作者设定为准。** 方案里来源是“作者”的项，AI 在生成方案时不能改动，只能通过提案卡提出修改。
- **两条作者设定互相矛盾时**，模型调用 `report_conflict`，给出两段原话和会受影响的体验。core 先逐字核对这两段原话确实出现在作者的输入里，核对不上的丢弃。不核实的话，就可能把模型编造的话当成作者原话。卡片上并列显示两段原话，作者就地修改。

## 9. 生成任务

向导按钮触发的生成都作为任务在后台运行。作者可以离开页面，回来时看到结果。

| 任务 | 用途配置 | 结果写到哪里 |
| --- | --- | --- |
| `plan`：生成故事方案 | `author_chat` | `meta.plan`。来自作者背景的项标为 `author`，AI 补全的项标为 `ai`。同时按背景所用的语言定下作品语言；作者改过作品语言的，不再覆盖（[i18n §6](./i18n.md#6-作品语言)） |
| `opening`：生成开场候选 | `narrator` | `meta.opening_candidates` |
| `title_blurb`：拟标题和简介 | `author_chat` | 发布确认页上的预填内容 |
| `trial_extract`：从试玩里提取人物设定 | `author_chat` | 一张 `propose_from_trial` 卡（§10） |

- **输入在任务开始时冻结。** 生成期间作者改了草稿，也不影响这次任务读取的内容。
- **写入结果和把任务标为完成在同一个事务里**，不会出现“结果已写入、任务却显示未完成”的中间状态。
- **写回前比较草稿的 `content_rev`**（[数据模型 §2](./data-model.md#2-作品与版本)）。不一致说明生成期间作者改过草稿：
  - `plan` 不覆盖草稿，结果进入对比视图，由作者决定采用哪些项；
  - `opening` 本来就只写候选，这时候选标上“基于修改前的草稿”；
  - `title_blurb` 和 `trial_extract` 不写作者设定，不受影响，`trial_extract` 出的卡在确认时另行复查。
- **失败时保留输入。** 方案还没生成就中断，回来时背景和设置都在；确认方案后开场生成失败，已确认的方案保留，可以直接重试。
- **core 重启时，运行中的任务改为失败**，原因记为 `interrupted`。
- **每局生成人物的作品，开场预览就是一次只到开场的试玩。** 它走[回合循环 §10](./turn-loop.md#10-开场)，用来让作者看看不同的人物怎样进入这个开场。

## 10. 试玩与带回作品

- **开始试玩：** 把草稿复制成试玩快照，新建一个 `kind=trial` 的开局，进入游玩页，页面标明“作者试玩”。回合循环和正式游玩完全相同，游玩页的全部操作也都可用：状态栏、手记、手动存档、从存档另开、换一种发展。
- **返回创作：** 回到草稿上次所在的步骤。
- **每次从开场重新试玩，都会新建一份快照**，所以试玩用的永远是当时的草稿。

**加入作品设定**的流程：

1. 作者在试玩正文里选中一个人物或一句对白，点“加入作品设定”。这是一个不经过对话模型的入口，带着选中的回合和段落。
2. 后台运行 `trial_extract` 任务，从这个人物在试玩中的档案和事实里提取候选项：身份、说话习惯、原话等。
3. 卡片上的每一项都可以单独勾选、修改。
4. **依赖检查：** 候选项里如果出现只在这次试玩中才有的东西，例如试玩中生成的其他人物、主角的试填姓名、试玩中发生的事件，就标出来，提醒作者改成通用说法。像“他替这位玩家修过表”这样的共同经历，默认不勾选。
5. 确认后，复制成草稿里的一条新作者设定：新 id，`origin_turn_id` 为空，和试玩里的任何行都不关联。试玩经历仍然独立。

## 11. 存入作品库与改稿

- **首次存入：** 作者确认标题、简介和已采用的开场。作者没写标题和简介时，先由 `title_blurb` 任务拟一份，作者可以直接采用。
- **存入就是发布：** 把草稿复制成发布版本，`works.published_id` 指向它（[数据模型 §2](./data-model.md#2-作品与版本)）。成功后显示“开始故事”和“返回作品库”；失败时草稿保留，并提供重试入口。
- **应用到新开局**是同一个操作。界面会说明：现有的 N 条路线继续使用原来的版本，从旧存档另开也沿用旧版本，只有新开局使用新版本。N 由查询得出。

## 12. 对话历史

每轮回复前，按预算装配历史：

1. **作者消息**优先，一律放原文；
2. **带卡的轮次**其次，按真实形状回放（§5）；
3. **其余 AI 回复**从新到旧放原文；
4. 放不下的部分省略，并在历史开头写明省略了多少轮。

每轮另外直接给出：当前步骤、锚点对象，以及草稿概要（标题、背景首段、方案里每一项的标题、开场首段）。其他内容由模型用只读工具自取。

模型调用时以线程 id 作为会话标识；生成任务以作品 id 作为会话标识（见 [LLM 端点 §5](./llm-endpoints.md#5-opencode-go)）。

> 已知限制：历史只按上面的优先级取舍，较早的 AI 回复既没有摘要行可以替代，也不会被压缩成检查点。很长的对话里，较早的 AI 回复会被整段省略。

## 13. 数据表

```sql
chat_threads (
  id             TEXT PRIMARY KEY,
  work_id        TEXT NOT NULL REFERENCES works ON DELETE CASCADE,
  created_at, last_active_at
)

chat_messages (
  id             TEXT PRIMARY KEY,
  thread_id      TEXT NOT NULL REFERENCES chat_threads ON DELETE CASCADE,
  role           TEXT NOT NULL,    -- author | assistant | system
  content        TEXT NOT NULL,
  anchor         JSON,             -- 作者消息：步骤、选中的对象、幕后设定是否已展开
  card           JSON,             -- 提案卡：动作、目标、改动、受影响的地方、问题
  tool_echo      JSON,             -- 回放用：提案工具的调用参数
  created_at
)

card_claims (
  card_message_id   TEXT PRIMARY KEY REFERENCES chat_messages ON DELETE CASCADE,
  decision          TEXT NOT NULL, -- confirmed | dismissed
  answers           JSON,
  result_message_id TEXT,
  created_at
)

jobs (
  id             TEXT PRIMARY KEY,
  work_id        TEXT NOT NULL REFERENCES works ON DELETE CASCADE,
  kind           TEXT NOT NULL,    -- plan | opening | title_blurb | trial_extract
  status         TEXT NOT NULL,    -- running | done | failed
  input          JSON NOT NULL,    -- 冻结的输入
  result         JSON,
  error          TEXT,
  created_at, updated_at
)
```

消息不可修改。卡片是待确认、已确认还是已搁置，从 `card_claims` 推导。删除消息时，提案卡、作者应答和回执三条一起删除，确认提示要写明会删掉几条。

## 14. 不做的事

- 跨会话的对话记忆。
- 对话历史的摘要行与检查点压缩（§12）。
- 多人协作编辑同一份草稿。

## 15. 验收

| 从什么情况开始 | 操作 | 应当看到的结果 |
| --- | --- | --- |
| 本机作品库为空 | 只写一句背景，不打开工作站，一路点完向导 | 得到可玩的作品 |
| 方案已生成，开场已采用 | 在对话里说“让两位主角开场就是旧识” | 卡上列出关系的变化，以及受影响的开场句子、关系栏和第一组选项；确认后，开场标为“待核对” |
| 一张待确认的卡 | 快速点两次确认，或在 core 独立运行时从两个浏览器标签页同时确认 | 只执行一次，两边看到同一份回执 |
| 一张待确认的卡，目标是某个人物 | 先在设定页手改这个人物，再确认卡片 | 卡片失效，提示目标已被修改；手改的内容保留 |
| 生成故事方案的任务正在运行 | 期间手改一项设定，等任务完成 | 方案没有直接覆盖草稿，而是进入对比视图等作者决定 |
| 幕后设定折叠 | 问 AI：“那个秘密到底是什么？” | AI 只能说出无剧透标题，说不出内容 |
| 试玩中认识了一位修表师 | 只把他的身份和一句口头禅加入作品，发布后新开一局 | 修表师会出现，也会说那句口头禅，但没有试玩里的共同回忆；那次试玩的路线仍可继续 |
| 两条作者设定互相矛盾 | 让 AI 检查方案 | 卡上并列显示两段原话，这两段话在作者输入里都能逐字找到 |
