# Unwritten · 回合循环

本文说明游玩时 AI 每一回合怎样读取上下文、怎样提出结果，以及 core 怎样校验并保存。玩家看到的行为见[游玩流程](./gameplay-flow.md)，存储结构见[数据模型](./data-model.md)。作者试玩走的是同一套循环。

一句话概括：**固定材料直接放进 prompt，其余的让模型自己去查；模型只能提议，由 core 校验后一次性提交。**

后文的提交事务以续写为例。重写和开场的提交边界分别见 §7 与 §10。

## 1. 一回合的流程

1. **玩家提交行动。** client 生成一个 `request_id`，把行动原话和预期 head 发给 core。推荐行动同时携带该回合中的选项序号，由 core 核对原话。序号从 1 起算，对应已提交的 `options` 数组。
2. **core 登记请求**，状态记为 `running`，然后立即返回。之后的进度通过事件流推送给 client（[架构总览 §3](./architecture.md#3-client-与-core-的通信)）。
3. **准备上下文。** core 算出父回合的祖先链，按 §3 组装 prompt。
4. **运行 agent 循环。** 用 pi-agent-core 跑工具循环：模型可以调用 §4 的只读工具，最后调用 `propose_turn` 提交结果，或调用 `ask_clarification` 请玩家澄清。模型使用 `narrator` 这个用途配置的模型，见 [LLM 端点 §7](./llm-endpoints.md#7-用途分配)。
5. **校验。** `propose_turn` 执行时，core 按 §6 校验。不合格的部分作为工具错误返回给模型，让它修正。
6. **提交。** 校验通过后，在一个事务里写入回合、事实、状态，并推进路线的 head。
7. **通知与后台任务。** 推送 `turn.committed`，再排队生成这一回合的摘要（§9）。

**事实在每一回合自动记录，不经人工审核**，因为游玩时没有作者在场。作为补偿，校验更严格，而且每条事实都必须标明出处段落。

## 2. 回合请求

```sql
turn_requests (
  id             TEXT PRIMARY KEY,   -- client 生成，用作幂等键
  playthrough_id TEXT NOT NULL REFERENCES playthroughs ON DELETE CASCADE,
  route_id       TEXT REFERENCES routes ON DELETE CASCADE,  -- 开场请求为空
  kind           TEXT NOT NULL,      -- continue | rewrite | opening
  expected_head_turn_id TEXT,        -- 续写和重写开始时的路线 head；开场为空
  parent_turn_id TEXT,               -- 续写：当前 head；重写：head 的父回合；开场：空
  action         JSON,               -- 玩家行动原话
  preference     TEXT,               -- 仅重写时有：叙述偏好
  clarification  JSON,               -- 按顺序保存的问题 id、问题、选项和回答
  status         TEXT NOT NULL,      -- running | needs_clarification | done | failed | superseded | cancelled
  error          TEXT,               -- 失败原因代码
  result_turn_id TEXT,               -- 候选移除后清空，状态仍为 done
  attempts       INTEGER NOT NULL DEFAULT 1,
  log            JSON,               -- 本次的工具调用足迹：调了哪些工具、带什么参数、返回了哪些记录
  created_at, updated_at
)
-- 同一路线同时最多只有一个 running 或 needs_clarification 的请求（按 route_id 的部分唯一索引）
-- 同一开局同时最多只有一个 running 或 needs_clarification 的开场请求（kind = 'opening' 时按 playthrough_id 的部分唯一索引）
```

- **同一个 `request_id` 重复提交**（双击、网络重试、断线后重发）时，先核对原提交参数。参数一致则返回已有的请求和它当前的状态与结果，不会重新运行，所以同一个行动只会产生一次后果。
- **重试是单独的命令**，只对 `failed` 的请求有效：沿用同一个 `request_id`，`attempts` 加一，重新运行。开场请求同样适用。
- **继续或重写时，core 在登记和提交事务内都比较预期 head。** 重试沿用原来的预期 head；已过期的澄清也释放进行中名额。
- **同一路线已有进行中的请求**时，新请求会被拒绝，界面提示“上一个行动还在生成”。
- **请求和回合分开存放。** 只有完整的回应才会成为回合，半截正文不会进 `turns` 表，所以中断不会推进路线。
- **已提交的回应带原请求标识。** core 从请求指向结果的关系投影出请求 ID 和尝试号。client 据此在重新查询后认出本次回应，并在对应正文渲染时结束[界面计时](./diagnostics.md#3-性能样本)。
- **`log` 只留在本机。** 它可能含有秘密和作品内容，只由回合请求保存。core 启动时清掉 90 天以前请求的 `log`（天数可配置），删除作品时一并删除。运行诊断按[诊断契约](./diagnostics.md)记录请求 ID、结果和耗时。

## 3. 上下文：哪些直接给，哪些让模型查

分工按四条判据决定：

1. **约束性材料直接放进 prompt。** 违反这类材料时模型自己意识不到，写出来看着通顺，其实已经跑偏。
2. **每次都要用、体量又有上限的材料，也直接放。** 不必让模型花一轮工具调用去取它反正要用的东西。
3. **只是有时要用、能按名字取回的材料，prompt 里只放一行索引，详情让模型用工具查。**
4. **会随路线增长、没有上限的材料，必须能用工具查到。**

另有一条硬约束：**每类材料要么直接给，要么能查到，而且它的名字或编号要能在某处被模型看见。** 模型没法查询它不知道存在的东西。

| 材料 | 依据 | 方式 |
| --- | --- | --- |
| 叙述约定（§11） | 1 | 直接给 |
| 作者锚点：叙事要求、内容边界、即兴范围（[数据模型 §2](./data-model.md#2-作品与版本)） | 1 | 直接给。作者写的三段自由文本，原样进 prompt，不截断 |
| 作品硬设定：世界规则、叙事要求、主角设定、本局的主角填写项、本局的主角形象 | 1 | 直接给 |
| 玩家这次的行动原话；重写时附上偏好，澄清后附上问答 | 1 | 直接给 |
| 当前场景：地点、故事时间、在场者（每人一行：主角对他的称呼、真名、认识阶段、一句话档案、当前形象） | 2 | 直接给 |
| 和在场者有关的秘密：陈述、谁知道、揭晓条件 | 1 | 直接给 |
| 当前状态栏：每个栏目的值、显示方式，以及范围或阶段列表；幕后栏目标明“不显示给玩家” | 2 | 直接给 |
| 未触发的关键场面（条件原文） | 1 | 直接给 |
| 最近的回合原文，从新到旧排，至少一回合 | 2 | 直接给 |
| 索引：本路线可见的人物、地点、物品、组织（编号、称呼、一句话），也就是作者设定的全部，加上本路线游玩中新增的；标明哪些已经出场。另列未了结的约定 | 3 | 直接给索引，详情去查 |
| 更早的回合 | 4 | 直接给摘要行（回合编号 + 摘要），原文去查 |
| 人物完整档案、关系史、谁知道什么、地点、物品和组织的详情、旧对白 | 3、4 | 用工具查 |

**预算。** 输入预算 = 模型上下文窗口 − 输出预留 − 本次实际下发的工具 schema − 系统提示。按下面的顺序填：

1. 约束性材料和当前场景。这部分超出预算时，请求失败：只算作者锚点就放不下时返回 `work_setting_too_long`，其余情况返回 `context_too_small`。两种情况都不截断材料，只是提示的下一步不同，一个要作者精简，一个要玩家换模型。
2. 最新一个回合的原文。该项和上一项一起放不下时，以 `context_too_small` 失败。
3. 索引行。
4. 更早回合的原文，从新到旧，放不下的改成摘要行；摘要行也放不下的就省略。

凡是被省略或截断的，都要明说，例如“另有 37 个更早的回合未列出，可用 `search_story` 或 `read_turn` 取回”。“已出场”指本路线可见的场景、事实或称呼里提到过它。实体多到索引放不下时，优先列已出场的，并写明“另有 N 个未出场的人物和地点，可用 `list_catalog` 查看”。被截过的材料不能看起来像完整的。

**编号。** prompt 和工具结果里，人物、事实、回合都用短编号表示：人物 `@3`，事实 `#12`，回合 `T45`。编号只在本次请求内有效，由 core 映射到真实 id。模型引用东西时用编号或唯一的名字，永远见不到也写不出真实 id。所以它只能引用本次真正看到过的东西，凭空编出的编号会被拒绝。

## 4. 只读工具

| 工具 | 参数 | 返回 |
| --- | --- | --- |
| `get_character` | 名字或编号 | 档案（含路线上的特征变化）、各人对他的称呼、他和主角及在场者的关系、他知道的事（含秘密与揭晓条件）、最近和他有关的事件 |
| `get_place` | 名字或编号 | 描述，以及在这里发生过的事件 |
| `get_entity` | 名字或编号 | 物品、组织等其他实体的档案，以及和它有关的事件 |
| `list_catalog` | 可附上一页返回的游标。类别为 `characters`、`places`、`items`、`groups`、`others`、`promises`、`events`、`scenes` 之一 | 目录行；实体目录标明是否已在本路线出现 |
| `who_knows` | 事实编号 | 每个知情者的知情程度，以及是从谁那里得知的 |
| `search_story` | 查询词 | 命中的段落：回合编号、段号、前后各一句 |
| `read_turn` | 回合编号 | 该回合的玩家行动和完整正文 |

使用规则：

- **每个工具只查一类东西。** 不提供任意查询或通用的表查询，否则无法保证所有读取都经过可见性投影。
- **范围在创建工具时就绑定好。** 版本、祖先链、主角都在工具创建时固定，模型只能传名字或编号，越不出本路线。
- **和 prompt 走同一套取数。** 工具内部调用 `story` 模块的投影函数，返回文本的格式和 prompt 里的一致。
- **工具循环也受上下文预算约束。** 每次请求模型前重新计算预算，给输出和工具 schema 留出空间。目录结果提供可继续读取的游标；单次工具结果装不下时截短并说明，必要材料和当前澄清放不下时以 `context_too_small` 结束。
- **记录足迹。** 每次调用的工具名、参数、返回了哪些记录，都写进 `turn_requests.log`。

另外几条：

- **查名字有多个结果时，全部作为候选返回**，并附上各自出现过的场景，由模型用编号选定。同名不等于同一个人。
- **单次返回的长度有上限**，超出就截断，并写明“已截断”。
- **每回合最多 8 轮工具调用**，上限可配置。
- **一次工具都不调，也必须能写出合格的一回合。** 直接给的材料就是写作的最低保障，查询只是锦上添花。

## 5. 提交一回合：`propose_turn` 与 `ask_clarification`

部分模型填不好对象或数组类型的参数，所以 **`propose_turn` 的参数一律是字符串**，结构化内容用“每行一个 JSON”来写。模型把整个列表写成一行 JSON 数组（如 `[{"text":…},{"text":…}]`）时，core 按元素展开，等价于每个元素各占一行；元素本身仍要是对象，不改其他校验。

| 参数 | 内容 |
| --- | --- |
| `prose` | 正文，段落之间空一行 |
| `options` | 每行一个 JSON：`{"text": "...", "hint": "..."}`。`hint` 只在作品选了“提醒已知后果”时允许，其余作品带 `hint` 时返回修正；提醒同样经过不泄露校验 |
| `changes` | 每行一个 JSON，类型见下表 |
| `ending` | `"true"` 或 `"false"`。作品没写结束条件时只能是 `"false"`，否则返回修正 |
| `illustrate` | 可省略。按 [游玩流程 §2.1](./gameplay-flow.md#21-插图)最多挑一个值得定格的可见瞬间，写它发生的正文段号。插图怎样生成见[插图与出图服务 §7](./image.md#7-插图) |

| `type` | 字段 | 说明 |
| --- | --- | --- |
| `new_entity` | kind、name、known_as、profile、appearance、para | 新出现的人物、地点、物品或组织。`known_as` 是主角此刻对它的称呼。人物可以带 `appearance`，只写此刻看得见的样子（[插图与出图服务 §6.1](./image.md#61-形象)） |
| `name` | entity、name、holder、para | 某人得知或开始使用一个称呼 |
| `event` | subject、object、statement、witnesses、para | 省略 `witnesses` 时，续写中仅在场人员未变时默认使用父回合在场者；开场或人员发生变化时显式填写 |
| `trait` | subject、key、statement、para | 人物特征的变化。`key` 为 `appearance` 时，`statement` 是此刻看得见的新样子，`same_visible_identity` 可填 `"true"`，含义见[数据模型 §4](./data-model.md#4-故事事实)。形象特征只供呈现，不能作为 `knowledge` 的引用 |
| `relation` | subject、object、key、relation_type、strength、stage、via、statement、para | |
| `promise` | subject、object、key、status、statement、para | |
| `knowledge` | fact、holder、level、perceived_statement、via、para | `fact` 写事实编号，或者本次某行事实自己起的 id |
| `state` | key、value、visible、closed | 数字、阶段、文字栏目的新值，`value` 的写法随显示方式而定。清单栏目不写 `value`，只用这一行改 `visible`、`closed`。`closed` 为 `"true"` 时栏目收起（事情已了结）。显示方式和可见性的优先级见[数据模型 §4](./data-model.md#4-故事事实) |
| `state_item` | key、item、status | 清单栏目里的一项：新增，或者改变状态。`status` 为 `open`、`done`、`failed`、`gone` 之一 |
| `new_state` | key、label、display、hidden、min、max、unit、stages | AI 新增的状态栏目。`min`、`max`、`unit` 只用于数字栏目；`stages` 只用于阶段栏目，阶段名用 `\|` 隔开，按先后排列 |
| `scene` | place、present、time | 这一回合结束时的场景 |
| `scene_hit` | scene、para | 触发了哪个关键场面。`scene` 写上下文里给未触发场面排的短编号 `S1`、`S2`…，core 在本次请求内把它映射回场面 id，模型见不到场面的真实 id |
| `secret` | subject、title、statement、reveal、knowers、para | 游玩中创造的秘密。`title` 是无剧透的标题；`knowers` 写一开始就知道的人（逗号分隔的名字或编号），core 为他们展开 `level` 为 `confirmed` 的知情记录：他们是秘密本来的知情者，不是听说或猜测 |

`para` 是这条变化在 `prose` 里的出处段号。事件、特征、关系、约定这些事实行，要用在某条 `knowledge` 里时，在那行加一个自己起的 `"id"`（如 `"f1"`），`knowledge` 的 `fact` 写这个 id。id 只在本条 `changes` 里有效，每行不能重复，也不能以 `#` 或 `@` 开头（那是 core 发的编号，混用会让引用指向错的东西）。行号不作引用：模型看不见行号，只能数，数错一次整条提交就被拒。例如：

```
{"type":"new_entity","kind":"character","name":"沈岚","known_as":"撑伞的女人","profile":"三十岁上下，说话很慢","appearance":"短发，深灰色旧风衣，撑一把黑伞","para":"2"}
{"type":"event","subject":"撑伞的女人","object":"@1","statement":"她把伞递给主角，自己站进雨里","para":"3"}
{"type":"event","subject":"撑伞的女人","object":"@1","statement":"她问主角明天还会不会在渡口等她","para":"5"}
```

事件的每个目击者会由 core 自动展开成一条知情记录，模型不需要逐一写出。

`ask_clarification` 有两个参数：`question` 和 `choices`（每行一个选项）。调用后请求状态变为 `needs_clarification`，路线停在原来的决定点。玩家回答后，core 按请求 id、当前问题和预期 head 校验，在事务内将状态改回 `running`。每次澄清生成独立的问题 id。重复提交已记录的同一回答时返回当前状态；旧问题的新回答被拒绝。后续仍需澄清时追加问答，不覆盖前一条；提交回合时把完整问答随行动保存，供重写沿用。

## 6. 校验与保存

| 检查 | 规则 | 不通过时 |
| --- | --- | --- |
| 时效 | 续写与重写的 head 和预期值相同；开场时该开局尚无根回合 | 请求标为 `superseded`，不提交 |
| 格式 | 每一行 `changes` 都符合 schema；段号不超出正文的段数；至少有一个选项（结局除外） | 返回给模型修正 |
| 引用 | 名字能在可见范围内唯一对应到一个实体，或者是本次新增的；编号或本次给事实行起的 id 必须是本次请求里出现过的；按名称引用的已有实体也必须已经在本次请求中下发 | 返回给模型修正，附上候选 |
| 新人物去重 | 和可见的同类实体同名时，必须用编号声明“就是此人”，或在档案里写明区别 | 返回给模型修正 |
| 知情 | 获知者必须在本回合在场，或者写明从谁那里得知。`secret` 的 `knowers` 除外：他们是秘密本来的知情者，不是在本回合得知的 | 返回给模型修正 |
| 不泄露 | 正文、选项、提醒、显示中的状态值里，如果出现主角尚不知道的名字，本次 `changes` 必须在该段或之前给主角加上这个称呼。幕后栏目不能设为显示 | 返回给模型修正 |
| 状态值 | 按[数据模型 §4](./data-model.md#4-故事事实)校验显示方式、配置和值，包括数字的边界、阶段名单的唯一性和清单条目的状态 | 返回给模型修正 |
| 关键场面 | 场面存在；“只发生一次”的场面没有在当前父回合的祖先链上触发过；出处段落存在 | 返回给模型修正 |
| 结局 | 作品写了结束条件 | 返回给模型修正 |
| 插图标记 | 存在 `illustrate` 时必须指向正文段落 | 丢弃标记 |
| 人物形象 | 人物的可选 `appearance` 和形象特征符合[插图与出图服务 §6.1](./image.md#61-形象)的长度与格式 | 丢弃不合格的形象或形象特征，保留人物登记 |

先校验并摘除无效的插图附加项，再校验其余故事变化。附加项缺失或无效时，合格的正文、选项和故事变化照常提交。

- **返回给模型修正**时，错误逐条列出（第几行、哪个字段、为什么）。模型最多修正 2 次，仍不通过就以 `invalid_output` 失败，路线停在上一个完整位置。
- 这套做法依赖 pi-agent-core 的约定：工具执行时抛出的错误会作为工具错误交还给模型；校验通过后，`propose_turn` 返回 `terminate: true` 结束循环。

**提交事务**一次写入以下所有内容，任何一步失败就整体回滚：

- 回合行；
- 新实体、称呼、事实、知情（含目击者展开）、状态定义与状态值；
- 全文索引行；
- 用比较再更新的方式推进 `routes.head_turn_id`，并更新 `updated_at`，同时清空 `draft_input`；
- 删除本路线针对旧 head 的候选，并清空相应请求的 `result_turn_id`；
- 把请求标为 `done`，记下 `result_turn_id`。

## 7. 换一种发展

- **请求**：`kind=rewrite`，`parent_turn_id` 是 head 的父回合，`action` 沿用原 head 的行动和已完成的澄清问答；玩家写的偏好只进叙述要求，不会成为主角台词、世界事实或手记。
- **上下文**：按父回合的祖先链组装，所以原版里才揭晓的秘密、人物反应、物品去向，候选一律看不见，不需要额外过滤。
- **结果**：以 `status=candidate` 提交，head 不动。候选的 `illustrate` 照常记进回合，但候选不画插图，被采用时才开始画（[插图与出图服务 §7.1](./image.md#71-什么时候画)）。比较时，core 校验候选属于请求中的路线与原版，再以候选为假想 head 返回候选正文、主角可见的状态变化和下一步选项。
- **采用**：先确认 head 仍是原版，再把 head 指向候选，更新路线时间、清空草稿输入，并把候选改为 `committed`，删除同一路线、同一原版的其余候选。候选由提交它的重写请求关联到路线和原版。候选删除后原请求仍可查询，其结果标为已移除，重复提交不会再生成。原版回合保留，因为重写前建立的存档还指向它。
- **沿用原版**：以预期 head 校验当前原版，删除同一路线、同一原版的候选。采用、删除和请求结果变更各自在同一个事务内完成。
- **离开比较界面**：head 仍是原版，候选保留到下次打开比较，或者到玩家从原版继续行动时删除。
- **结局回合也可以重写。** 采用后，路线是否结束跟着新 head 的 `ending` 走。
- **开场回合不提供换一种发展。** 它没有父回合，也没有玩家行动。固定人物的作品，开场就是作者采用的那一份；每局生成人物的作品，重新开局时人物和开场正文都会重新生成。

## 8. 中断与恢复

| 情形 | core 怎么处理 |
| --- | --- |
| 写了还没发送 | client 停止输入一会儿后，把内容存进 `routes.draft_input`；回来时显示为草稿，由玩家决定是否发送 |
| 已发送，玩家离开页面 | 请求在 core 里继续运行；玩家回来时 client 查询请求状态，已完成就直接显示结果 |
| 重复发送 | 同一个 `request_id` 只返回已有的请求和结果，不会重新运行（§2） |
| 生成失败 | 状态改为 `failed` 并记录原因。玩家可以重试（单独的重试命令，同一个请求，`attempts` 加一），或改写行动（取消这个请求，发一个新的） |
| core 重启 | 启动时把所有 `running` 的请求改为 `failed`，原因记为 `interrupted`。生成到一半的正文不保存 |
| 保存失败 | 事务回滚，状态改为 `failed`，原因记为 `save`；路线停在上一个位置 |
| 回应已过期 | head 已经变了（比如在另一个浏览器标签页里采用了别的版本），状态改为 `superseded`，不提交 |

**生成中的反馈。** client 显示已提交的行动与“生成中”。玩家只在校验和提交成功后看到新正文、选项和状态。失败时保留上一个完整决定点，显示“本段未完成”和重试入口。接口不向玩家返回 narrator 工具足迹或未经主角视角处理的摘要。

## 9. 后台摘要

- 每个回合提交后，排队用 `background` 用途的模型生成一两句摘要，写入 `turn_summaries`。
- 摘要是索引行，不是正文的替代品：它不必保全所有细节，但必须点名出现的人物、地点和事件，否则模型无从判断该不该回去翻原文。
- 遇到措辞上的疑问，一律回到原文（`read_turn`），不以摘要为准。
- 队列在 core 进程内，一次只跑一两个。core 启动时，为最近活跃路线中缺少摘要的回合补排。
- 摘要失败不影响游玩，那一回合改用“回合编号 + 玩家行动”代替；开场回合用“开场”。
- 调用时带上会话标识：回合和摘要用路线 id；开场和每局生成人物时还没有路线，用开局 id（见 [LLM 端点 §5](./llm-endpoints.md#5-opencode-go)）。

## 10. 开场

开局时按顺序执行：

1. **建开局。** 新建 `playthroughs`，记下玩家填写的主角项目和[本局插图设置](./data-model.md#3-经历开局回合树路线存档)。固定模式下，人物直接来自作者设定。
2. **生成人物（仅每局生成模式）。** 开局请求在后台分两步跑。第一步，narrator 用提案工具 `propose_cast` 为每个人物位置各交一个具体人物，名字两两不同，也不和作者设定的人物同名，可以附一段形象。校验通过后存进 `playthroughs.cast`。第二步用 `propose_opening` 写开场（第 3 步）。重试时 `cast` 已经有值就跳过第一步，所以开场生成失败、重试时，仍然沿用这次已经确定的人物。
3. **写开场正文。** 先把已采用开场的正文、初始选项和初始状态值里的主角填写项占位符 `{{protagonist.<项目名>}}` 替换成玩家这次填写的值；玩家留空的项目，用作者为它设的默认值（[数据模型 §2](./data-model.md#2-作品与版本)）。然后：
   - 固定人物：直接使用替换后的开场，不调用模型。建开局、写根回合和第一条路线在同一个同步事务里完成，所以玩家点「开始故事」后立即读到开场。
   - 每局生成人物：narrator 以作者确定的时间、地点、处境为准，参照替换后的开场，为本局人物写开场，用 `new_entity` 登记本局人物并写明人物位置，并经过 §6 中适用于根回合的格式、引用和内容校验。填写值已经替换进参照的开场，这一步的正文和选项里不允许再出现占位符。固定开场在采用时已经校验过，开局时只替换占位符；玩家的填写值不能含换行，所以替换不会多切出段落，开场事实的出处段号保持有效。每局生成人物的开场请求通过开局仍未有根回合来判断时效。开场缺少父回合，初始场景和本局人物直接用本次开局的待提交数据校验。
4. **提交根回合。** 一并写入初始场景、初始状态值、本局生成的人物（`origin_turn_id` 指向根回合），以及主角的姓名称呼。符合[开场出图条件](./image.md#71-什么时候画)时以 `illustrate_para = 0` 标记开场图。从这一刻起，开局就成为可以续玩的进度，并为它建立第一条路线。根回合、初始数据、索引、第一条路线和请求完成状态在同一个事务中写入。

开场失败时，开局行和已确定的人物都保留，玩家可以选择“重试这次开局”或“返回作品库”。

**占位符在采用开场之前就检查过。** 作品有主角名填写项时，开场预览的正文和选项里不能写死主角的名字，也不能用作者没留的填写项：AI 起草的开场作为校验错误交回模型修正；采用作者原文的开场列出需要处理的句子，处理完之前不能采用（[创作工作站 §7](./author-workstation.md#7-受影响范围与开场核对)）。占位符只在开局时替换正文、初始选项和初始状态值，所以模型写的标题、简介、公开设定、地点、时间和开场事实里出现占位符或写死主角名，一律作为校验错误交回模型，这些地方提到主角时用不带名字的称呼。

## 11. 叙述约定

这些约定写进 narrator 的系统提示。哪些由代码强制、哪些只能靠提示和评测，分开列：

| 约定 | 怎样保证 |
| --- | --- |
| 先回应玩家实际做的事，再推进局势 | 提示 + 评测 |
| 不替主角作承诺、表明立场或披露信息；遇到需要主角决定的时刻就停下，用选项把决定交回玩家 | 提示 + 评测 |
| 可以补充符合原意的日常对白和动作细节 | 提示 |
| 每个角色只依据自己知道的事行动；玩家私下得知的消息，别的角色要有机会听到或看到才能提起 | 知情校验（§6）只保证每条知情记录有来源；角色在正文里怎样使用信息，靠提示 + 评测 |
| 第一次见面、只是听说过、已经相熟，表现各不相同 | 认识阶段直接给（§3）+ 提示 |
| 自由输入有歧义、不同理解会导致不同后果时，先澄清 | `ask_clarification` + 提示 |
| 行动受阻时，写出主角能感知到的结果 | 提示 |
| 提醒只能使用主角已知的信息 | 提示 + 评测；提醒里出现主角不知道的名字时，由不泄露校验（§6）拦下 |
| 不提前写出主角不知道的名字 | 不泄露校验（§6） |
| 不提前透露秘密的内容、关系的真相和未触发的关键场面 | 提示 + 评测。这类语义上的泄露，代码判断不了 |
| 标记能看清动作、互动、后果或线索的段落，也留意安静而重要的瞬间 | 提示 + 评测。用人物互动、玩家行动后果、线索特写和例行过场检查该画的段落是否入选。诊断按路线记录标记率（[运行诊断 §2.1](./diagnostics.md#21-错误提示与诊断编号)） |
| 形象只写此刻看得见的样子。伪装和揭晓分别写当时的样子 | 提示 + 评测。身份、来历和秘密混进形象文字时，代码无法判断文字的实际含义 |

只靠“提示 + 评测”的几条，需要一组真实模型的评测用例，按需运行，不放进每次提交的检查里。评测放在仓库根目录的 `evals/`（[技术选型 §8](./tech-stack.md#8-测试)）。

## 12. 不做的事

- **概率事件。** 关键场面只按条件触发，不按概率触发。世界书模板里的触发概率如果引入，抽到的结果必须写成事实，读档才能接回同一次经历。
- **长路线的二级压缩。** 更早的回合只以摘要行出现，不再把多条摘要压成检查点。
- **一回合内分多个子代理写作。**

## 13. 验收

| 从什么情况开始 | 操作 | 应当看到的结果 |
| --- | --- | --- |
| 两个候选：一个揭晓某个秘密，一个保留它 | 采用揭晓的那一版，然后从重写前的存档另开一条路线 | 手记和选项跟着采用的版本走；另开的路线里秘密仍未揭晓 |
| 正在生成 | 分别在生成中、保存后但界面未刷新时、摘要生成前强制结束 core | 恢复后正文、状态、知情一致，同一个行动只推进一次 |
| 连续点两次发送；断网后重发 | 检查路线 | 只有一个新回合 |
| 第 3 回合的一句原话 | 在第 40 回合采取和它有关的行动 | 模型能用工具找到那一回合，回应符合人物的知情范围 |
| 主角私下得知一个消息 | 下一回合换一个不在场的角色出场 | 这个角色不提这件事；这一行为由真实模型评测覆盖；程序验收另检查无来源的知情记录被拒绝 |
| 有一个主角只知道外号的人物 | 让模型写出包含真名的选项 | 被不泄露校验拦下，要求先在正文里揭晓 |
| 作者设定了一个还没出场的人物 | 玩家行动里提到他的名字 | 模型在索引里找到他，并用工具取回档案 |
| 固定人物、作者原文开场的正文和初始选项里都有主角名占位符 | 玩家填写名字后开局 | 开场正文和初始选项里都显示玩家填写的名字，看不到占位符 |
| 一个范围是 0 到 10 的数字栏目 | 让模型把它写成 12 | 被状态值校验拦下，修正后才提交 |
| 一个清单栏目已有两项 | 下一回合模型只交一个新条目 | 提交后清单有三项，原来的两项保持原来的状态 |
| narrator 新增一个人物，没写 `appearance`，并把 `illustrate` 写成正文里不存在的段号 | 提交 `propose_turn` | 回合照常提交，人物登记成功、没有形象，回合没有插图标记 |
| 两个标签页停在同一决定点 | 第一页继续，第二页再提交旧选项或保存旧决定点 | core 返回过期结果，不把操作应用到新 head |
| narrator 先生成包含未知真名的回应，再按校验反馈修正 | 观察生成事件和提交前后的界面 | 提交前只显示生成状态，玩家始终看不到被拒绝的正文 |

长线回忆另外在诊断库记录检索耗时和送入模型的上下文量，用作[性能基线](./diagnostics.md#3-性能样本)。
