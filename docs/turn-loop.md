# Unwritten · 回合循环

本文说明游玩时 AI 每一回合怎样读取上下文、怎样提出结果，以及 core 怎样校验并保存。玩家看到的行为见[游玩流程](./gameplay-flow.md)，存储结构见[数据模型](./data-model.md)。作者试玩走的是同一套循环。

一句话概括：**固定材料直接放进 prompt，其余的让模型自己去查；模型只能提议，由 core 校验后一次性提交。**

## 1. 一回合的流程

1. **玩家提交行动。** client 生成一个 `request_id`，把行动原话发给 core。
2. **core 登记请求**，状态记为 `running`，然后立即返回。之后的进度通过事件流推送给 client（[架构总览 §3](./architecture.md#3-client-与-core-的通信)）。
3. **准备上下文。** core 算出父回合的祖先链，按 §3 组装 prompt。
4. **运行 agent 循环。** 用 pi-agent-core 跑工具循环：模型可以调用 §4 的只读工具，最后调用 `propose_turn` 提交结果，或调用 `ask_clarification` 请玩家澄清。模型使用 `narrator` 这个用途配置的模型，见 [LLM 端点 §7](./llm-endpoints.md#7-用途分配)。
5. **校验。** `propose_turn` 执行时，core 按 §6 校验。不合格的部分作为工具错误返回给模型，让它修正。
6. **提交。** 校验通过后，在一个事务里写入回合、事实、状态，并推进路线的 head。
7. **通知与后台任务。** 推送 `turn.committed`，再排队生成这一回合的摘要（§9）。

**事实在每一回合自动记录，不经人工审核**，因为游玩时没有作者在场。作为补偿，校验更严格，而且每条事实都必须标明出处段落。

## 2. 回合请求

```sql
turn_requests (
  id             TEXT PRIMARY KEY,   -- client 生成，用作幂等键
  playthrough_id TEXT NOT NULL REFERENCES playthroughs ON DELETE CASCADE,
  route_id       TEXT REFERENCES routes ON DELETE CASCADE,  -- 开场请求为空
  kind           TEXT NOT NULL,      -- continue | rewrite | opening
  parent_turn_id TEXT,               -- 续写：当前 head；重写：head 的父回合；开场：空
  action         JSON,               -- 玩家行动原话
  preference     TEXT,               -- 仅重写时有：叙述偏好
  clarification  JSON,               -- 澄清的问题、选项和玩家的回答
  status         TEXT NOT NULL,      -- running | needs_clarification | done | failed | superseded | cancelled
  error          TEXT,               -- 失败原因代码
  result_turn_id TEXT,
  attempts       INTEGER NOT NULL DEFAULT 1,
  log            JSON,               -- 本次的工具调用足迹：调了哪些工具、带什么参数、返回了哪些记录
  created_at, updated_at
)
-- 同一路线同时最多只有一个 running 或 needs_clarification 的请求（部分唯一索引）
```

- **同一个 `request_id` 重复提交**（双击、网络重试、断线后重发）时，直接返回已有的请求和结果，所以同一个行动只会产生一次后果。
- **同一路线已有进行中的请求**时，新请求会被拒绝，界面提示“上一个行动还在生成”。
- **请求和回合分开存放。** 只有完整的回应才会成为回合，半截正文不会进 `turns` 表，所以中断不会推进路线。

## 3. 上下文：哪些直接给，哪些让模型查

分工按四条判据决定：

1. **约束性材料直接放进 prompt。** 违反这类材料时模型自己意识不到，写出来看着通顺，其实已经跑偏。
2. **每次都要用、体量又有上限的材料，也直接放。** 不必让模型花一轮工具调用去取它反正要用的东西。
3. **只是有时要用、能按名字取回的材料，prompt 里只放一行索引，详情让模型用工具查。**
4. **会随路线增长、没有上限的材料，必须能用工具查到。**

另有一条硬约束：**每类材料要么直接给，要么能查到，而且它的名字或编号要能在某处被模型看见。** 模型没法查询它不知道存在的东西。

| 材料 | 依据 | 方式 |
| --- | --- | --- |
| 叙述约定（§11） | 1 | 直接给 |
| 作品硬设定：世界规则、叙事要求、主角设定、本局的主角填写项 | 1 | 直接给 |
| 玩家这次的行动原话；重写时附上偏好，澄清后附上问答 | 1 | 直接给 |
| 当前场景：地点、故事时间、在场者（每人一行：主角对他的称呼、真名、认识阶段、一句话档案） | 2 | 直接给 |
| 和在场者有关的秘密：陈述、谁知道、揭晓条件 | 1 | 直接给 |
| 当前状态栏，幕后栏目标明“不显示给玩家” | 2 | 直接给 |
| 未触发的关键场面（条件原文） | 1 | 直接给 |
| 最近的回合原文，从新到旧排，至少一回合 | 2 | 直接给 |
| 索引：本路线已出现的人物和地点（编号、称呼、一句话），未了结的约定和事件 | 3 | 直接给索引，详情去查 |
| 更早的回合 | 4 | 直接给摘要行（回合编号 + 摘要），原文去查 |
| 人物完整档案、关系史、谁知道什么、地点详情、旧对白 | 3、4 | 用工具查 |

**预算。** 输入预算 = 模型上下文窗口 − 输出预留 − 本次实际下发的工具 schema − 系统提示。按下面的顺序填：

1. 约束性材料和当前场景。这部分超出预算时，请求以 `context_too_small` 失败，提示玩家换一个上下文更长的模型。不截断约束性材料。
2. 最新一个回合的原文。
3. 索引行。
4. 更早回合的原文，从新到旧，放不下的改成摘要行；摘要行也放不下的就省略。

凡是被省略或截断的，都要明说，例如“另有 37 个更早的回合未列出，可用 `search_story` 或 `read_turn` 取回”。被截过的材料不能看起来像完整的。

**编号。** prompt 和工具结果里，人物、事实、回合都用短编号表示：人物 `@3`，事实 `#12`，回合 `T45`。编号只在本次请求内有效，由 core 映射到真实 id。模型引用东西时用编号或唯一的名字，永远见不到也写不出真实 id。所以它只能引用本次真正看到过的东西，凭空编出的编号会被拒绝。

## 4. 只读工具

| 工具 | 参数 | 返回 |
| --- | --- | --- |
| `get_character` | 名字或编号 | 档案（含路线上的特征变化）、各人对他的称呼、他和主角及在场者的关系、他知道的事（含秘密与揭晓条件）、最近和他有关的事件 |
| `get_place` | 名字或编号 | 描述，以及在这里发生过的事件 |
| `list_catalog` | `characters`、`places`、`promises`、`events`、`scenes` 之一 | 目录行 |
| `who_knows` | 事实编号 | 每个知情者的知情程度，以及是从谁那里得知的 |
| `search_story` | 查询词 | 命中的段落：回合编号、段号、前后各一句 |
| `read_turn` | 回合编号 | 该回合的玩家行动和完整正文 |

使用规则：

- **每个工具只查一类东西。** 不提供任意查询或通用的表查询，否则无法保证所有读取都经过可见性投影。
- **范围在创建工具时就绑定好。** 版本、祖先链、主角都在工具创建时固定，模型只能传名字或编号，越不出本路线。
- **和 prompt 走同一套取数。** 工具内部调用 `story` 模块的投影函数，返回文本的格式和 prompt 里的一致。
- **记录足迹。** 每次调用的工具名、参数、返回了哪些记录，都写进 `turn_requests.log`。

另外几条：

- **查名字有多个结果时，全部作为候选返回**，并附上各自出现过的场景，由模型用编号选定。同名不等于同一个人。
- **单次返回的长度有上限**，超出就截断，并写明“已截断”。
- **每回合最多 8 轮工具调用**，上限可配置。
- **一次工具都不调，也必须能写出合格的一回合。** 直接给的材料就是写作的最低保障，查询只是锦上添花。

## 5. 提交一回合：`propose_turn` 与 `ask_clarification`

部分模型填不好对象或数组类型的参数，所以 **`propose_turn` 的参数一律是字符串**，结构化内容用“每行一个 JSON”来写。

| 参数 | 内容 |
| --- | --- |
| `prose` | 正文，段落之间空一行 |
| `options` | 每行一个 JSON：`{"text": "...", "hint": "..."}`。`hint` 只在作品开启“提醒已知后果”时填写 |
| `changes` | 每行一个 JSON，类型见下表 |
| `ending` | `"true"` 或 `"false"` |

| `type` | 字段 | 说明 |
| --- | --- | --- |
| `new_entity` | kind、name、known_as、profile、para | 新出现的人物或地点。`known_as` 是主角此刻对它的称呼 |
| `name` | entity、name、holder、para | 某人得知或开始使用一个称呼 |
| `event` | subject、object、statement、witnesses、para | 省略 `witnesses` 时，默认为本回合的在场者 |
| `trait` | subject、key、statement、para | 人物特征的变化 |
| `relation` | subject、object、type、strength、stage、statement、para | |
| `promise` | subject、object、key、status、statement、para | |
| `knowledge` | fact、holder、level、via、para | `fact` 写事实编号，或者本次 `changes` 里前面某一行的行号 |
| `state` | key、value、visible | |
| `new_state` | key、label、display、hidden | AI 新增的状态栏目 |
| `scene` | place、present、time | 这一回合结束时的场景 |
| `scene_hit` | scene、para | 触发了哪个关键场面 |

`para` 是这条变化在 `prose` 里的出处段号。例如：

```
{"type":"new_entity","kind":"character","name":"沈岚","known_as":"撑伞的女人","profile":"三十岁上下，说话很慢","para":"2"}
{"type":"event","subject":"撑伞的女人","object":"@1","statement":"她把伞递给主角，自己站进雨里","para":"3"}
{"type":"promise","subject":"撑伞的女人","object":"@1","key":"明早渡口","status":"proposed","statement":"她问主角明天还会不会在渡口等她","para":"5"}
```

事件的每个目击者会由 core 自动展开成一条知情记录，模型不需要逐一写出。

`ask_clarification` 有两个参数：`question` 和 `choices`（每行一个选项）。调用后请求状态变为 `needs_clarification`，路线停在原来的决定点。玩家回答后，**同一个请求**带着问答继续运行。

## 6. 校验与保存

| 检查 | 规则 | 不通过时 |
| --- | --- | --- |
| 时效 | 续写时父回合仍是 head；重写时 head 仍是被重写的那个回合 | 请求标为 `superseded`，不提交 |
| 格式 | 每一行 `changes` 都符合 schema；段号不超出正文的段数；至少有一个选项（结局除外） | 返回给模型修正 |
| 引用 | 名字能在可见范围内唯一对应到一个实体，或者是本次新增的；编号必须是本次请求里出现过的 | 返回给模型修正，附上候选 |
| 新人物去重 | 和可见的同类实体同名时，必须用编号声明“就是此人”，或在档案里写明区别 | 返回给模型修正 |
| 知情 | 获知者必须在本回合在场，或者写明从谁那里得知 | 返回给模型修正 |
| 不泄露 | 正文、选项、提醒、显示中的状态值里，如果出现主角尚不知道的名字，本次 `changes` 必须在该段或之前给主角加上这个称呼。幕后栏目不能设为显示 | 返回给模型修正 |
| 关键场面 | 场面存在；“只发生一次”的场面没有触发过；出处段落存在 | 返回给模型修正 |
| 结局 | 作品写了结束条件 | 返回给模型修正 |

- **返回给模型修正**时，错误逐条列出（第几行、哪个字段、为什么）。模型最多修正 2 次，仍不通过就以 `invalid_output` 失败，路线停在上一个完整位置。
- 这套做法依赖 pi-agent-core 的约定：工具执行时抛出的错误会作为工具错误交还给模型；校验通过后，`propose_turn` 返回 `terminate: true` 结束循环。

**提交事务**一次写入以下所有内容，任何一步失败就整体回滚：

- 回合行；
- 新实体、称呼、事实、知情（含目击者展开）、状态定义与状态值；
- 全文索引行；
- 用比较再更新的方式推进 `routes.head_turn_id`，并更新 `updated_at`，同时清空 `draft_input`；
- 删除被这次续写淘汰的候选；
- 把请求标为 `done`，记下 `result_turn_id`。

## 7. 换一种发展

- **请求**：`kind=rewrite`，`parent_turn_id` 是 head 的父回合，`action` 沿用 head 的行动；玩家写的偏好只进叙述要求，不会成为主角台词、世界事实或手记。
- **上下文**：按父回合的祖先链组装，所以原版里才揭晓的秘密、人物反应、物品去向，候选一律看不见，不需要额外过滤。
- **结果**：以 `status=candidate` 提交，head 不动。比较时，client 把候选当作假想的 head 来投影，从而显示候选自己的正文、状态变化和下一步选项。
- **采用**：先确认 head 仍是原版，再把 head 指向候选，候选改为 `committed`，其他候选删除。原版回合保留，因为重写前建立的存档还指向它。
- **沿用原版**：删除候选。
- **离开比较界面**：head 仍是原版，候选保留到下次打开比较，或者到玩家从原版继续行动时删除。
- **结局回合也可以重写。** 采用后，路线是否结束跟着新 head 的 `ending` 走。

## 8. 中断与恢复

| 情形 | core 怎么处理 |
| --- | --- |
| 写了还没发送 | client 停止输入一会儿后，把内容存进 `routes.draft_input`；回来时显示为草稿，由玩家决定是否发送 |
| 已发送，玩家离开页面 | 请求在 core 里继续运行；玩家回来时 client 查询请求状态，已完成就直接显示结果 |
| 重复发送 | 同一个 `request_id` 返回已有结果（§2） |
| 生成失败 | 状态改为 `failed` 并记录原因。玩家可以重试（同一个请求，`attempts` 加一），或改写行动（取消这个请求，发一个新的） |
| core 重启 | 启动时把所有 `running` 的请求改为 `failed`，原因记为 `interrupted`。生成到一半的正文不保存 |
| 保存失败 | 事务回滚，状态改为 `failed`，原因记为 `save`；路线停在上一个位置 |
| 回应已过期 | head 已经变了（比如在另一个窗口采用了别的版本），状态改为 `superseded`，不提交 |

**生成中的预览。** pi-ai 能把工具参数随生成流式推送出来。core 把 `prose` 这一段边生成边推给 client，界面标明“生成中”。预览不落库：提交成功后换成正式回合，失败时显示“本段未完成”和重试入口。

## 9. 后台摘要

- 每个回合提交后，排队用 `background` 用途的模型生成一两句摘要，写入 `turn_summaries`。
- 摘要是索引行，不是正文的替代品：它不必保全所有细节，但必须点名出现的人物、地点和事件，否则模型无从判断该不该回去翻原文。
- 遇到措辞上的疑问，一律回到原文（`read_turn`），不以摘要为准。
- 队列在 core 进程内，一次只跑一两个。core 启动时，为最近活跃路线中缺少摘要的回合补排。
- 摘要失败不影响游玩，那一回合改用“回合编号 + 玩家行动”代替。
- 调用时带上路线 id 作为会话标识（见 [LLM 端点 §5](./llm-endpoints.md#5-opencode-go)）。

## 10. 开场

开局时按顺序执行：

1. **建开局。** 新建 `playthroughs`，记下玩家填写的主角项目。固定模式下，人物直接来自作者设定。
2. **生成人物（仅每局生成模式）。** narrator 为每个人物位置生成具体人物，先存进 `playthroughs.cast`。这样开场生成失败、重试时，仍然沿用这次已经确定的人物。
3. **写开场正文。**
   - 固定人物，并且采用作者原文或已采用的开场：直接复制，不调用模型。
   - 每局生成人物：narrator 以作者确定的时间、地点、处境为准，为本局人物写开场，并经过 §6 的同一套校验。
4. **提交根回合。** 一并写入初始场景、初始状态值、本局生成的人物（`origin_turn_id` 指向根回合），以及主角的姓名称呼。从这一刻起，开局就成为可以续玩的进度，并为它建立第一条路线。

开场失败时，开局行和已确定的人物都保留，玩家可以选择“重试这次开局”或“返回作品库”。

## 11. 叙述约定

这些约定写进 narrator 的系统提示。哪些由代码强制、哪些只能靠提示和评测，分开列：

| 约定 | 怎样保证 |
| --- | --- |
| 先回应玩家实际做的事，再推进局势 | 提示 + 评测 |
| 不替主角作承诺、表明立场或披露信息；遇到需要主角决定的时刻就停下，用选项把决定交回玩家 | 提示 + 评测 |
| 可以补充符合原意的日常对白和动作细节 | 提示 |
| 每个角色只依据自己知道的事行动；玩家私下得知的消息，别的角色要有机会听到或看到才能提起 | 知情校验（§6）+ 提示 |
| 第一次见面、只是听说过、已经相熟，表现各不相同 | 认识阶段直接给（§3）+ 提示 |
| 自由输入有歧义、不同理解会导致不同后果时，先澄清 | `ask_clarification` + 提示 |
| 行动受阻时，写出主角能感知到的结果 | 提示 |
| 提醒只能使用主角已知的信息 | 不泄露校验（§6）+ 提示 |
| 不提前透露主角不知道的名字和秘密 | 不泄露校验（§6） |

只靠“提示 + 评测”的几条，需要一组真实模型的评测用例，按需运行，不放进每次提交的检查里。评测放在仓库根目录的 `evals/`（[技术选型 §8](./tech-stack.md#8-测试)）。

## 12. 不做的事

- **概率事件。** 关键场面只按条件触发，不按概率触发。世界书模板里的触发概率如果引入，抽到的结果必须写成事实，读档才能接回同一次经历。
- **长路线的二级压缩。** 更早的回合只以摘要行出现，不再把多条摘要压成检查点。
- **语义检索。** 检索只用 trigram 全文检索和短查询的子串扫描。
- **一回合内分多个子代理写作。**

## 13. 验收

| 从什么情况开始 | 操作 | 应当看到的结果 |

| 两个候选：一个揭晓某个秘密，一个保留它 | 采用揭晓的那一版，然后从重写前的存档另开一条路线 | 手记和选项跟着采用的版本走；另开的路线里秘密仍未揭晓 |
